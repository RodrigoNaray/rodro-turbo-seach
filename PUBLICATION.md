# Publication preparation / Preparación para publicar

This is a maintainer checklist, not a release announcement. The project remains
a functional MVP, maintained on a personal, best-effort basis. Preparation changes
are local: no repository rename, visibility change, push, or release is performed.

## GitHub presentation

Current remote spelling: `RodrigoNaray/rodro-turbo-seach`. Keep it unless the owner
explicitly requests a rename. Application name: **Rodro Turbo Search**.

Suggested description:

> Lightweight application launcher for GNOME/Wayland, built with Rust and GTK4, with a calculator and optional filename search.

Suggested topics:

`rust`, `gtk4`, `gtk-rs`, `linux`, `gnome`, `wayland`, `application-launcher`,
`desktop-search`, `calculator`, `gpl-3-0`

These are suggestions, not settings applied to GitHub. “Lightweight” describes the
design goal; no measured advantage over another launcher is asserted.

## Before changing visibility

1. The documentation, license, metadata, and packaging changes are committed in
   `8a99ece`. The untracked alternative SVG is excluded; the app uses v2-rayo, so
   that unused file does not need a decision before publishing this branch.
2. The owner confirmed authorship of the original logo artwork. Keep upstream
   notices, including the DejaVu glyph attribution. GPL-3.0-only applies to original
   project work; dependencies and font-derived material retain their own notices.
3. Inspect `git log --all --format='%h %ae %ce'` and the intended outgoing diff.
   The reviewed reachable history uses GitHub noreply addresses. Old local,
   unreachable commits may remain after a prior email correction; they are not
   sent in a normal branch push. Do not upload `.git` directories, private Git
   bundles, or old history backups. If old commit links/copies exist on GitHub or
   elsewhere, publishing the rewritten branch does not erase those copies.
4. Decide whether to clean local reflogs/unreachable objects after preserving a
   private backup. That is a separate, potentially destructive operation requiring
   explicit authorization; this preparation does not rewrite or purge history.
5. Check repository settings manually: enable Issues if desired; enable private
   vulnerability reporting before advertising it as active; add the description
   and topics. No GitHub Actions workflows existed to preserve or validate.
6. Re-run checks on the intended commit. Review desktop focus/drag manually, and
   remove private filenames/clipboard data from any demonstration.
7. Only then choose visibility and publish through the owner's normal workflow.
   This checklist does not change visibility or authorize a push.

## Binary distribution

Do not upload `target/` or the entire working directory as a source release.
The local packaging script includes the binary, installer, license, and notices;
it is not a complete corresponding-source archive. For a future binary release,
provide the matching source, required linked dependencies, and build/install
scripts under a GPLv3-compliant source delivery method. For example, prepare a
source archive with the exact lockfile and `cargo vendor --locked` output plus its
configuration, and verify it builds offline before publishing source and binary
together. No vendor tree or release is generated by this documentation change.
